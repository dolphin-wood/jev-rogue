# Jev に問いかけて分かったこと

[English](jev-findings.md) · [简体中文](jev-findings.zh-CN.md) · **日本語**

実際の Jev（TypeSafe の `choice` モデル）に対して Director を調整する中で得た発見を、次の質問を書くときに踏まえられるよう記録します。各項目には、観察したこと、その根拠、いまの対応を書きます。特記がない限り、数字は同じ 8 シード、`average` の技量プロファイルで行った route review と `pnpm answer-stats` の結果です。

引用符内の state、選択肢、instruction の原文は英語のまま残します。それが Jev に送られる文字どおりの内容だからです。

## Jev の答え方

Jev は `state` と互いに独立した質問の組を読み、質問ごとに選択肢上の確率分布を返します。Jev は**分類器**です。一つの state に対して、どの選択肢が合うかを答えます。呼び出しをまたいで計画せず、以前の答えを覚えず、数えず、数値を比べず、推論を連鎖させません。各質問はそれぞれ単独で答えられます。

## 発見

<a id="finding-0"></a>

### 0. 「どれも合わない」と言える唯一の手段は退避用の選択肢である
Jev は常に合計 1 の完全な分布を返します。そのため、どの選択肢も state に合わないときでも、どれか一つが先頭に来て、抽選はそれに従って動きます。「ここに合うものはない」とモデルが言える唯一の方法は、まさにその意味の選択肢を用意することです。そこで各質問には `fallback`（"None of these fits; let the game decide."）を付けています。選択肢の範囲外になりうる入力に対して Jev のドキュメントが勧めている方法です。これが選ばれた場合、その質問は **declined（辞退）** として記録され、ルールテーブルが答えます。
- 辞退は Jev の答えであり、故障ではありません。state か選択肢が判断材料を与えていないと言っています。最初の部屋の見た目に関する質問（選択肢が前の部屋との関係でしか定義されていない）はすべて辞退され、それが欠けている履歴を直接指していました。
- したがって**質問ごとの辞退率**は診断指標になります。よく辞退される質問は、state が根拠を与えられない選択肢を持っています（例：spec を直す前の `stat_family` は 17%）。
- 通常の選択肢に高い確率が付いても、それが合う証拠にはなりません。退避用の選択肢がなければ、最も間違いの少ない答えが自信ありげに見えます。退避用の選択肢に乗る確率は、モデルがその一覧をどれだけ信頼しているかとして読みます。
- 順位付けには退避用の選択肢を入れません（扉に「どれも合わない」と表示はできません）。また、コードはそれだけを問う質問を作りません。
- **信頼度はその代わりになりません。** Jev の `confidence` は分布がどれだけ尖っているかから計算されます。平らなら低く、一つの山なら高くなります（ドキュメントは 0.3–0.5 未満の答えを人に回すよう勧めています）。これが測るのは「この中のどれか」の曖昧さであって、「どれかが合うか」ではありません。すべての選択肢が間違っていても、最も間違いの少ないものが山を作り、自信があるように読めます。ラベル照合型の条項の下でまさにそれを見ました（`stat_family` の信頼度は 0.54 なのに、問いの 17% が退避用の選択肢に行っていた）。つまり、退避用の選択肢は「どれも合わない」に答え、信頼度は「どれを、どれだけ確かに」に答えます。ゲームでは、許容できる選択肢の間の平らな答えは他へ回すべき問題ではありません。そこから抽選することが変化を生みます。信頼度の下限が意味を持つのは、一度の誤りがランを台無しにする判断だけです。


### 1. どの state にも合う選択肢はどの state でも勝つ
変化しない state のラベルがあると、それを根拠にした選択肢はどこでも合ってしまい、質問は条項を最も多く持つ選択肢で決まります。`mana_sustain` は 56 部屋中 50 部屋で `tight` でした（実際のプレイではなく、模擬的な詠唱ループからの予測でした）。そして stat の扉がポータルの質問を 99% で取りました。
**いま：**state にはプレイの実測値だけを区分して載せ、予測や結論は載せません。動かないラベルは見つけるべきバグです。

### 2. 「向かないもの」を持たない選択肢が吸い込み口になる
`what` / `not_for` / `examples` 形式の選択肢では、`not_for` を持たない選択肢にあらゆる state が落ちていきます。`subspecies: none` 71%、`elite_presence` 81%、`dim` に肯定的なケースがなかったときの `mood_brightness` は bright が 81%。
中間の選択肢すべてに `not_for` を付けると、`mood_particles` は 96% から 55% になりました。
**いま：**手書きでも生成でも、すべての選択肢が自分のデータから書いた `not_for` を持ちます。手書きの spec にそれがなければテストが失敗します。

<a id="finding-3"></a>

### 3. 例は、ある質問ではノイズであり、別の質問では仕組みそのものである
`anchor` から二つの例を削除しただけで（他は変えずに）、`tank` 56% から `none` 99% になりました。汎用的な例を一つずつ戻すと 86% に戻りました。`stat_family` も同様でした。density、waves、entry、zone の枠では、例を外すと*改善*しました。
**ルール：**選択肢が*それが何であるか*（説明）で異なる場合、例はノイズで過学習を招きます。選択肢が*どの state の行が当てはまるか*だけで異なる場合、例こそ Jev が対応関係を学ぶ手段です。そこにだけ、汎用的な例を少数置きます（`briefing.test.ts` がその一覧を固定しています）。

### 4. 一つの選択肢を擁護する instruction は答えを決めてしまう
instruction は選択肢より先に読まれます。レベルが上がるとマナコストが上がると説明する二つの条項だけで、マナの問題がほとんど測定されていない state でも `stat_family` は 95% `mana` になりました。“`none` is a real answer” と書いた zone の instruction は `none` を擁護していました。
**いま：**instruction は原則を公平に述べ、どの一文も一つの選択肢を擁護しません。

<a id="finding-5"></a>

### 5. 多様性を求めると答えはかえって集中する
Jev には同じ扉を出し続けていることが見えません。呼び出しは毎回新しい分類であり、“the affix badge has been on the last 4 offers” は分類器にとって、affix の選択肢に合うもう一つの事実にすぎません。同じ種類の扉が続いた最長回数の実測値：コードの上限ありで 5、なしで 7。上限なしで、連続回数を state に書き、繰り返される表示についての `not_for` を全種類に付け、多様性の原則を brief に入れると **10**（affix の割合 48% → 60%）。
見た目の質問も同じです。規範的な一文 “the next room should not look the same” を単なる事実に置き換えると、平均の最頻値の割合が 59% から 72% に上がりました。
**ルール：**多様性は*系列*の性質であり、分類器が答えるのは *state* です。系列の性質はコード（抽選、ソフトなペナルティ、上限）に属し、言い回しには属しません。`DOOR_STREAK_CAP` は残します。

<a id="finding-5a"></a>

### 5a. 選択肢を強調する語りはそれを押し上げ、中立的な件数は動かさない
対照実験：固定した一つの briefing（空いたキーが一つ、空いた affix 枠が四つ）、実際の spec を使った `portal_need` の質問、変えるのは一文だけ、それぞれ実際の呼び出しを 15 回。`affix` の平均確率：

| 加えた一文 | affix |
|---|---|
| なし | 3% |
| "The player has said they want more affixes." | 78% |
| "The player has said they do not want any more affixes." | 0% |
| "The affix slots, affix tiers and affix cards of the build are the ones listed above."（語を繰り返すだけで新しい意味はない） | 4% |
| "Doors: the affix badge has been on each of the last 4 offers." | 7% |
| "…the affix badge has been on the last 4 offers, and the player walked past it every time." | 16% |
| "…over the last 4 rooms the player walked past the affix door each time it was offered." | 32% |
| "…over the last 4 rooms the player chose the spell or stat door every time, never the affix door." | 44% |
| "Spell doors and stat doors have hardly appeared lately." | 2%（spell は 81% → 90%） |

つまり語の頻度ではありません。語を繰り返しても何も起きず、述べられた希望や拒否は否定も含めて正確に読まれます。しかし、**ある選択肢をめぐるプレイヤーの行動の履歴はその選択肢を押し上げ**、文がその選択肢にこだわるほど上がります。その行動が避けていることでもです。Jev は「プレイヤーは affix を選ばないでいる」を「これは affix の話だ」と読みます。「最近ほとんど出ていない」も埋め合わせにはならず、名指しされた種類を押し上げました。
二回目の実験で*言い回し*と*内容*を切り分けました。同じ履歴を中立的な件数で書くと、何も動きません。

| 加えた一文 | affix |
|---|---|
| なし | 3% |
| "Doors taken in the last 4 rooms: spell 2, stat 2." | 3% |
| "Doors taken in the last 4 rooms: spell 2, stat 2, affix 0." | 7% |
| "Doors offered in the last 4 rooms: affix 4, spell 3, stat 3, gold 2. Doors taken: spell 2, stat 2." | 4% |
| 同じ四部屋を一部屋一行の平叙文で（"Room 3: offered affix, spell, stat; took spell."） | 3% |

選択肢を押し上げたのは事実ではなく、**強調的で物語的な枠組み**（“every time”、“never”、“walked past it each time”）でした。中立的な件数は安全ですが、同時に無力です。Jev の答えを変化させません。
**ルール：**履歴は平叙の件数と部屋ごとの平叙の行で書き、強調語（“every”、“never”、“always”、“room after room”、“most/least”）も、一つの選択肢を中心に組み立てた文も使いません。プレイヤーが実際に述べた希望（本人の言葉）は正しく読まれます。多様性と回避はコードの仕事です（発見 5）。

### 6. state に算術を書いても、Jev が一度も上位にしない選択肢は動かない
五回のランそれぞれ約 100 部屋で、gold が最大の需要になった回数は 0 でした。次の商人で金貨が何を買えるかを briefing に書く前も後もです。扉の 7% という割合は、コードが短い順位付けを最も長く出ていない種類で埋めた結果にすぎません。
**ルール：**ある選択肢を一定の頻度で出す必要があるなら、それはコードの下限であり、事実ではありません。

### 7. Jev は数えないので、件数は一行で渡す
連続回数、「前回の息抜き以来の戦闘数」、「直近 3 枚中 3 枚がスタイル外」は、コードが計算してそれぞれ一行で書きます。Jev が順にたどって数えなければならないリストは、Jev が使える事実ではありません。

### 8. 未測定はゼロと同じではない
ランの開始時、事実の既定値は「ダメージなし、息抜き直後」で、これが `peak` のすべての条項に合っていました。どのランでも部屋 1 が `peak` になりました。
**いま：**未測定の事実はそう書きます（“no room played yet”）。部屋 1–2 は `peak` になれません（コードの制約）。

### 9. テスト用の固定値が答えに漏れる
`affix_intent` が 100% `wider` と答えたのは、ハーネスが開始プリセットを `spam` に固定し、意図を入力していなかったためです。プリセットと意図を変えると 41 / 32 / 27 になりました。
**ルール：**質問は多様な入力で評価します。偏った答えはモデルではなく固定値のせいかもしれません。

### 10. 同じ事実に基づく二つの質問は一つの質問である
symmetry と三つの mood の質問は、同じ体力 / ダメージ / 撃破速度の区分に基づいており、一つの質問として答えられていました（91–100% が同じ答え）。
**いま：**見た目の質問はそれぞれ独自の交互性の事実と、実際に動く事実を最大一つだけ持ちます。

### 11. 結論は内容のテキストに隠れている
設計者向けに書かれたアイテムの説明（“at the lowest mana cost in the attack pool”、“suits a spam build”）が選択肢のテキストとして Jev に届き、答えとして読まれていました。**いま：**選択肢と state のテキストは、パラメーターかプレイヤー向けの説明から書き、設計メモからは書きません。

### 12. 散文の state は答えだけでなく信頼度も変える
ラベル照合型の条項では、照合に意味があるかどうかに関係なく Jev は高い信頼度で答えます（`stat_family` は辞退 17% なのに 0.54）。散文の briefing は平均信頼度を下げ（0.68 → 0.60）、ラン全体の結果を改善しました（報酬がビルドの需要に合う 40% → 49%、呪文レベルの上昇 62% → 71%、`stat_family` の辞退 17% → 0%）。信頼度は形式をまたいで比べられる品質スコアではありません。

### 13. 一つの温度では順位付けに対応できない
先頭の扉は鋭く、残りは広く抽選するには二つの温度が必要です（`PORTAL_NEED_TEMPERATURE`、`PORTAL_TAIL_TEMPERATURE`）。鋭い値一つだけでは、どの部屋も同じ三つの表示になりました。

### 14. 運用
- 上流の `529`（過負荷）は実際に起きます。evaluator は部屋の締め切り内でバックオフしながら再試行し、ルール側に切り替えます。
- カードプール全体を含む第 1 ラウンドのリクエストは約 52 KB です。クライアントとプロキシの本文サイズ上限を引き上げる必要がありました。
- プレイヤー自身の言葉をキーワードで解釈すると誤ります（“clear rooms fast” がマナへの不満と読まれた）。文は Jev に読ませるほうがよいです。

### 15. 質問で得ようとした系列の性質は、結局すべてコードに書いた
一度の作業で三つ、どれも同じ形でした。設計意図は*ラン*についてのもので、質問は *state* についてのものであり、意図を運ぶはずの言い回しが一つの選択肢の擁護に変わりました。

| ランを通して変化させたいもの | 文章での表現 | 実測 | いま |
|---|---|---|---|
| 部屋の見た目 | 見た目の質問の instruction に交互性を書き、各要素がどれだけ続いたかを数える state の行を加えた | `mood_particles` `calm` 91%、`mood_temperature` 65%、`symmetry` 58% | 連続回数の行を削除し、意図は instruction に残し、抽選前に前の部屋の答えへ `LOOK_REPEAT_PENALTY`（0.33） |
| 部屋に優先目標があるか | instruction **と** `none` の両方に “a run needs both, or the rooms that do have something to aim at stop reading as different” | `anchor` `none` 85%。両方からこの文を削除して 87% | 前の部屋の anchor に同じ 0.33 のペナルティ |
| 報酬に出すカード | なし。報酬は Jev の適合度順位だけ | 1 ランで見る affix は 20 種中 8.4、呪文は 25 種中 9.0。上位五つが枠の 73–75% を占めた | `CARD_REPEAT_PENALTY`（一度出るごとに 0.45 倍、下限 0.12）と、プールに未提示のカードがあれば末尾に一枚保証 |

見た目と anchor はきれいな例です。**文章を削っても何も動かず**（`anchor` 85% → 87%）、コードの項はすぐに効きました。ルールは発見 5 そのもので、無視すると代償を二度払います。答えで一度、問うのに使ったトークンで一度です。

<a id="finding-16"></a>

### 16. state を中立にすると、狙っていない質問まで動いた
発見 5a のルール（平叙の件数、強調語なし、一つの選択肢を中心にした文なし）を briefing 全体に適用すると、扉から遠く離れた答えまで変わりました。8 シード、`average`、briefing 側、変更前後：

| 質問 | 変更前 | 変更後 |
|---|---|---|
| `mood_particles`（コードのペナルティ前の生の答え） | `calm` 91% | `calm` 72% |
| `mood_temperature` | `cold` 54% | `warm` 54%（両者の差は 16 ポイント以内に） |
| `elite_portal` | `none` 58% | `none` 86% |
| `stat_family` | `survival` 75% | `survival` 42%、`movement` 39% |
| `subspecies` の辞退 | 15% | 9% |

見た目の質問は触れずにほぐれました。連続回数の行こそが、その質問自身の答えにこだわる文だったのです。`elite_portal` は逆方向に 30 ポイント近く動きましたが、変更はそれを何も狙っていませんでした。つまり state の編集はリクエスト内の*すべて*の質問への変更であり、直したい質問だけを測る作業は、壊した質問を見落とします。

### 17. gold に必要なのは論証ではなく下限、商人には上限
`portal_need` は **101 部屋で 0 回** `gold` を一位にしました。財布、商人の値段、両者で何が買えるかを state に書く前も後もです。扉に占める割合はすべて順位付けの末尾から来ていました。`GOLD_FLOOR_ROOMS`（gold が直近五回の報酬に出ていなければ一覧に加える）でポータルの 7% から 8% になりました。これは下限の効果であって、説得ではありません。

商人はその裏返しでした。ポータルの 10% に対し gold は 7%。部屋 2–12 の間で二部屋、四回の提示という上限の下で、1 ランあたり 1.5 回の中盤の商人部屋がありました。プレイからは「ゲームがお金を使わせようとしている」と報告されました。一部屋、二回の提示、部屋 4–10 の範囲にすると、gold の 8% に対して 3% になりました。

### 18. プール全体に当てはまる否定は、絞り込みではなく辞退になる
変異体の順位付けの `not_for` は “a room the player meets no ordinary <base> in” で始まっていました。敵の編成は次のラウンドで決まるので、これはほぼすべての部屋のほぼすべての選択肢に当てはまります。*すべて*の選択肢が state に合わないとき、合うものはなく、退避用の選択肢が答えを取ります。順位付けは部屋の 15% で辞退し、退避用の選択肢に 0.21 が乗りました。base を `what` に移し、否定を選択肢ごとに異なるタグだけから書くと、辞退は 9% になりました。
発見 2 の裏返しで、ルールは同じです。プール全体について書いた文は、どちらを向いていても何も区別しません。

### 19. 一つの選択肢を名指す制約では、二つの選択肢の連続を止められない
`DOOR_STREAK_CAP` は「直近四回の報酬すべてに出ていた種類」を外しますが、`doorStreakSpent` は固定の順序でそのような種類の**最初の一つ**だけを返していました。四種類から三つの扉を引くと、ほとんどの報酬に二種類が重なるので、二種類が一緒に続くことがよくあります。あるランでは部屋 1 から 4 まで spell *と* affix が出て、上限は spell を外し、affix は名目上の上限四を超えて五回目に進みました。8 シード、`average` での実測：上限「オン」で同じ種類の最長連続は 5。
**いま：**`doorStreaksSpent` は上限に達したすべての種類を返し、それらはすべて一覧から外れます。下限として報酬の種類を二つ残します。
**ルール：**選択肢の集合について書いた制約は、その最初の要素ではなく集合全体で評価しなければなりません。上限が自分の値 + 1 で測定されるなら、それは調整の問題ではなくバグです。

### 19a. それでも上限は必要：なければ十回続く
発見 5 は文章がリクエストに残った状態で連続を測りました。文章を**すべて外した**状態で測り直しました。中立的な briefing、連続回数なし、どの選択肢にも表示の繰り返しについての記述なし、`DIRECTOR_BRIEF` に多様性の段落なし。8 シード、16 部屋のラン、120 回の報酬：

| 表示 | 上限なしでの最長連続報酬数 |
|---|---|
| affix | 10 |
| spell | 7 |
| stat | 6 |
| gold | 2 |

文を外すと、それらが選択肢を*押し上げる*ことはなくなりましたが（発見 5a）、その文が目指した多様性には何の効果もありませんでした。理由は同じログに見えています。`portal_need` は `build_shape` を鋭く読みます（raw 88% spell、forming 54% affix、formed 43% stat）。そしてランは 16 部屋のうち 10 部屋を `forming` で過ごします。どの答えも自分の state については正しく、それらが作る系列は一つの表示になります。**`DOOR_STREAK_CAP` は残し**、リクエストには多様性を擁護する記述を一切入れません。

### 20. 吸い込み口は、主張が最も長く否定が最も狭い選択肢である

| `size` | `standard` 88%（`compact` 0%） | 条項 1 つ | 商人の部屋について書かれていた |
| `next_tension` | `build` 85%（`release` 1%） | “the pitch most rooms sit at” | 条項 2 つ |

どの質問でも、最頻の選択肢の `what` は最後に自分を擁護していました。`none` は “is the only room where what the player has learnt this run is simply true”、`build` は “the pitch most rooms sit at”。発見 4 の誤りが instruction から選択肢へ、一つ左の欄に移っただけです。そしてどの質問でも、隣の選択肢が留保を背負っていました。`elite_presence: one` の否定は三条項、`none` は一条項でした。

### 21. instruction が名指せるのは state が印字している事実だけ
`subspecies_weight` の instruction は “how far the run has come, **how many rooms have been plain already** and how the player's build is doing” から答えるよう求めていました。briefing はそれを一度も書いていませんでした。部屋にいた変異体は敵の一覧にそれぞれの名前で載っていたので、求められたとおりに答えるには 13 個の id を見分けてから部屋を数える必要がありました。どちらも分類器はしません（発見 7）。結果として 70% が `none` でした。
**いま：**コードが数え、pitch がすでに受け取っているのと同じ形で state が書きます。“Rooms whose bodies were all ordinary: 4 of the 6 fought” と “Fights since the last room with a variant body in it: 3”。
**ルール：**instruction が事実を名指すことは、state がその事実を導き出せる何かではなく*一行*として載せるという約束です。

### 22. gold は財布を読まない。どちらの方向にも

### 23. 違う量を名指す選択肢は、読みやすくても間違っている
`density` は部屋が**戦闘全体を通して**抱える敵の数を決めます。同時に床に立つ数はランの進行に応じた増加の設定が決め、どの答えもそれを変えません。両端の選択肢は逆のことを言っていました。“few bodies on the floor at once: a breather”、“many bodies at once: the hardest crowd the run currently allows”。質問はゲームが作らない部屋を説明しており、12 体が 4 体ずつ来る序盤の部屋では、プレイヤーが出会うものの逆を説明していました。
**いま：**選択肢はラウンドごとの `DENSITY_TARGETS` を引用し、instruction は数が合計であって同時の群れではないと一度だけ言い、state は部屋の二つの上限を載せます（“Bodies this room may hold over its whole fight: 12”、“Bodies that stand on the floor at once in this room: at most 4”）。8 シード、103 部屋で測ると答えは散らばりました。normal 75% → 58%、sparse 10% → 25%、dense 14% → 17%。最初の試みでは `sparse` の `what` 自体にけなす一文（“the one answer that leaves the floor emptier than this room would allow”）を入れてしまい、**1%** まで下げ、質量の十分の一が退避用の選択肢に行きました。その論評を除いた数字が上のものです。

**そして Director には直せない同等性の問題。**目標数に部屋のラウンド数を掛け（`targetCount`）、増加設定の合計で切ると、組み立て器はどの部屋番号、どの pitch でも `normal` と `dense` に*同じ編成*を返し、`sparse` もわずかに小さいだけでした。実測では部屋 7 の `build` で sparse が 12–13 体、他の二つがどちらも 12–16 体。部屋 14 の `peak` で 12–19 対 12–20 と 12–20。選択肢のテキストは何を求めているかについて正直です。部屋がそれをどう扱うかは `packages/core` の問題です。
**ルール：**選択肢が数字を引用するなら、ゲームが実際に使っている定数から引用し、その定数が何の量かを名指します。

### 24. 行き詰まった質問は触れなくてもほぐれることがある
見た目が部屋のカンマ区切りの一覧に埋もれていたとき、`mood_brightness` は 97% が同じ答えで、`dim` に肯定的なケースが書かれていなかったときは 81% でした。いま測ると（その間、明るさに関する変更は何もありませんが、state が中立化され（発見 16）、見た目に専用の行ができました）、97 回の問いで `dim` 52% / `bright` 48% です。退避用の質量 0.09 はリクエスト内のどの質問よりも高く、これは正直な読みです。二つの薄い選択肢の間で、state が本当に決め手を持っていません。
**ルール：**行き詰まった質問の一覧は古くなります。直す前に測り直さないと、作業はすでに自然に直った質問に費やされ、壊れた質問を見落とします（発見 16 を逆側から見たもの）。

### 24a. 一行に一つの事実、そして例はその行を引用する
前の部屋の見た目の四要素は一つのカンマ区切りで届いていました（“Last room's look: mirrored layout, warm light, dim, busy particles”）。そのため四つの見た目の質問はそれぞれ一つの節だけを読み、残り三つを無視していました。また各質問の例は、briefing が実際に印字する行になるために四つすべてを引用する必要があり、そのうち三つはその質問が決めないフィールドの具体値でした。四行に分けると、各質問の例は自分の答えを読み取る一行そのものになります（“Last room's brightness: bright”）。

8 シード、16 部屋のランで、**プレイヤーが実際に入る部屋**について測りました（生の答えは部屋ではありません。間に `LOOK_REPEAT_PENALTY` があります）：

| 見た目 | 同じ部屋の最長連続、前 → 後 | 平均連続 |
|---|---|---|
| symmetry | 9 → 4 | 2.4 → 1.6 |
| temperature | 12 → 6 | 3.1 → 1.8 |
| brightness | 10 → 7 | 2.1 → 1.5 |
| particles | 16 → 8 | 5.1 → 2.1 |

最頻値の割合はほとんど動いていない（56/54/60/60% → 58/56/55/58%）ので、答えが考えを変えたのではありません。事実を無視するのをやめ、*事実を追う*ようになったのです。その結果、生の分布は強く集中しました。`symmetry` は 99% が asymmetric でした。ペナルティがすでに前の部屋を mirrored にしており、質問はいまそれを読んでいるからです。これは交互に切り替わる質問の正直な形であって、行き詰まりではありません。コードが交互に切り替えるものは、割合ではなく系列を見ます。

### 25. briefing が二度印字する区分の境界は自己矛盾する
state は測定量ごとに数値と区分の両方を示すので、切り方の誤りは一行で見えます。`hits_per_shot` は `v >= 1` で区切られており、毎発ちょうど一体に当てるプレイヤーは **“Bodies struck per shot fired: 1.0, reads as several”** と読まれます。定数のコメントは、この区切りを「それより上なら呪文は貫通か分裂している」という意味で置いたと言っているので、ラベルは一区分ずれています。そして追尾 affix の系統と報酬の `eases` という事実は、このラベルから読まれます。（`packages/core/src/run/observed.ts` の `hitsPerShotSeveral`。ここでは直していません。core の担当です。）
**ルール：**区分の横に数値を印字する価値はトークンに見合います。切り方を誤った区分が自ら姿を現す唯一の場所です。

### 26. 同等性のルールは法則ではなく、二つの質問はそのせいで悪化した
発見 20 の修正（最頻の選択肢の主張を一条項に削り、隣の選択肢の留保も同じだけ削る）を一度に四つの質問に適用し、各段階で同じ八シード、同じプロファイルで測りました。二つは正しい方向に、二つは間違った方向にさらに進みました。

| 質問 | 前 | 同等化後 | 二回目の修正後 |
|---|---|---|---|
| `elite_presence` `none` | 83% | 76% | — |
| `density` `normal`（件数修正済み、発見 23） | 75% | 64% | 57%、`sparse` 10% → 24% |
| `size` `standard` | 88%、`vast` 18% | **100%**、`vast` 0% | — |
| `subspecies_weight` `none` | 66% | **90%** | **100%** |

`size` と `subspecies_weight` は、測定結果のよかったテキストに戻しました。二つのことが言えます。一つ目は、選択肢の長さは重みであってレバーではないことです。最頻の選択肢の主張を短くすると論拠が一つ減り、state がその質問に他の材料を与えていないところでは、読むものが少なくなった安全な答えが残ります。二つ目は `subspecies_weight` の二回目の修正です。state は自身の instruction が求めていた事実 “how many of the fights so far held a variant body” を得ましたが、どの書き方でも（片側だけ、次に両側の集計）答えはさらに `none` に寄りました。変異体のいないランでは、この事実は「このランはずっと普通だった」としか言えないからです。一つの選択肢についてしか語らない件数は、集計の形をしていてもいなくても、その選択肢の擁護になります。

どちらの質問も一つの答えかその近くで止まっており、言葉で言えることはもう残っていません。次に試すべきはより良い文ではなく、発見 6 と 17 が gold について行き着いた頻度の下限です。変異体なしで N 部屋が続いたら `none` を選択肢から外す。`size` も同様にするか、質問ごと外す。**どちらも未実装です。** 制約はユーザーが決めることで、作業の一回が決めることではないので、ハードルールの見直しへの提案です。

### 27. Jev が一度も選ばない選択は頻度であり、頻度はコードの仕事である
ハードルールの見直しの後、三つの質問が state に何が書かれていても一つの答えにとどまっていました。`subspecies_weight` は 100% `none`、`size` は発見 26 の書き直しの後 100% `standard` でした。`next_tension` が `release` と答えたのは 1% で、13 戦続けて息抜きがなく、ハートが一つしか残っていなくても 0% でした。言葉でできるレバーはすべて試しました。中立的なテキスト、長さの同等化、instruction が求めた事実、自己擁護の条項の削除。どれも答えを稀な選択肢へ動かさず、いくつかはさらに遠ざけました。

**決定（ユーザー、2026-09-25）：**稀な答えには gold と同じく**ルールの下限**を設けます（発見 17）。変異体なしで N 部屋が続いたら、`none` を `subspecies_weight` の一覧から外します。息抜きなしで N 部屋が続いたら、次の pitch は `release` になりえます。`size` も同じ扱いで、N 部屋 `standard` が続いたら一覧から外します。残ったものは引き続き Jev が順位付けするので、範囲内でどの変異体、どのサイズ、いつかは、Director による state の読みが決めます。コードが決めるのは、稀な選択肢がいずれ起きることだけです。

**ルール：**ある質問の稀な選択肢がゲームにとって重要なのに、どの state でも Jev がそれを選ばないなら、それは**系列の性質**です。この state に何が合うかではなく、ラン全体で何かがどれだけの頻度で起きるかの問題です。選択肢のテキストで擁護するのではなく、コードに下限として書きます。症状は、その選択肢を有利にするよう設計した state でも稀な選択肢が 0% 前後にとどまることです。下限を足す前に、まず発見 24 を確認して測り直します。行き詰まった質問は自然にほぐれることがあるからです。

### 過去との関係でしか定義されない選択肢は、最初の問いでは当てはまるものがない
四つの見た目の質問の選択肢は前の部屋を軸に書かれています（“…whose last floor was already mirrored”）。部屋 1 には前の部屋がなく、実際のセッションの最初の部屋で Jev は四つすべてを辞退しました。
**いま：**最初の部屋の見た目は問いません。ルールテーブルが埋め、判断は辞退ではなく `no_history` として記録されます。**ルール：**選択肢が履歴との関係でしか意味を持たない質問は、履歴ができるまで問いません。

### 28. 中立的なカードテキストは Jev の答えを何も変えなかった。スタイルへの偏りは Jev 自身のもの（2026-09-25）

### 33. Jev の答えは温度越しではなく信頼度で読む（2026-09-25）
TypeSafe は Choice を、その `choice`（最も確率の高い選択肢）を `confidence` で判定するものとして説明しています。信頼度は分布の広がりから計算され（`(n × peak − 1) / (n − 1)`）、自信のある答えには従い、低い答えはモデルが分からないと言っているものとして扱います。Director はそうせず、すべての答えを質問ごとの温度（ほとんどは 0.4）で抽選していました（doc 002：argmax はプレイを決めない。さもないと一つの state が常に一つの部屋を作る）。1 未満の温度は、Jev の二番目の選択肢を Jev が言ったよりも弱く読み直します。位置を示した原則（発見 32）の下で Jev は前の school に 0.46 を置きましたが、0.4 ではそれが 78% の確率で繰り返しとして戻ってきました。

オフラインで、実際のラン四回の記録済みの答え（60 部屋、規則ごとに 2,000 回の抽選。後の答えは実際に起きた履歴を条件にしているので、これは予測ではなく方向性です）：

| 規則 | Jev の一位から外れる | 前回と同じ | 最長連続 | 最多の答えの割合 |
|---|---|---|---|---|
| 質問ごとの温度（出荷時） | 18% | 60% | 5.1 | 71% |
| 常に `choice` | 0% | 68% | 6.0 | 77% |
| 信頼度 ≥ 0.5 なら `choice`、それ未満は分布どおり | 20% | 60% | 5.1 | 71% |

信頼度による読み方は、質問ごとの数値なしで全体として温度と同等であり、原則がもたらす迷いが別の答えになるのはここです。再送した `spell_school` のリクエストで、前の school が戻ってきた割合は、温度で 65%、常に `choice` で 82%、信頼度による読み方で 31% でした。常に `choice` を取ると `symmetry` が固定されます（100% 繰り返し、平均連続 11.8）。

**いま：**Jev が答える質問は、信頼度 ≥ 0.5（TypeSafe の推奨する下限、`JEV_CONFIDENT`）なら `choice` を取り、それ未満なら分布そのままから抽選します。信頼度は、コードが選択肢を絞り、繰り返しのペナルティをかけた後に実際に抽選する分布の上で計算した TypeSafe の統計量です。ルール側とランダム側は温度を保ち、順位付け（`portal_need`、`subspecies`）とカードの抽選も同様です。代償：Jev が常に確信している質問はいま固定されます。`size` は部屋の 92% で `standard`、あるランの stat の扉は十回続けて survival でした。

**ルール：**Jev の答えは TypeSafe のドキュメントどおりに受け取ります。確信があれば `choice`、なければ分布です。温度は Jev の不確かさを設計者が読み直すものであり、私たちが求めたまさにその迷いを隠していました。

### 34. カードと切り離して決めた約束は繰り返す。扉は開くときに、背後のカードと一緒に決める（2026-09-25）
spell の扉は school を約束していました（部屋の第 2 ラウンドで問う専用の質問）。その先の報酬にはその school のカードを必ず一枚含め、stat の扉は family を約束していました。位置を示した原則と信頼度による読み方があっても、実際のラン四回で spell の扉の 68% が前の spell の扉の school を繰り返しました。school は代理指標です。プレイヤーが欲しいのは自分のスタイルの呪文であり、一つのスタイルは複数の school にまたがります（void には spam の呪文も nuke の呪文もあります）。上位二つか三つの school を問う形にしても役に立ちませんでした。Jev の順位は安定しており、ランのすべての扉で上位二つは同じ組でした（storm + void 10 回中 10 回、spirit + stone 7 回中 7 回）。

### 35. プール全体への choice は「どれが答えか」を聞いている。カードは一枚ずつ聞く（2026-09-27）
プレイからの報告：Jev アームでは一部の呪文と affix がほとんど出てこない。`pnpm card-exposure` で測定した（十ラン、スタイルを回し、各リクエストの回答で Director 自身の抽選を再生）：39 呪文のうち 17 が一様抽選の四分の一未満の露出で、最も冷たいものは 0.01、上位十枚が 72% を占めた。同じシードのルールアームでは四分の一未満はゼロ、最も冷たいもので 0.67。

## ここから導かれる常設ルール
- State：プレイからの事実を言葉で書き、件数は事前に計算する。結論も規範も書かず、造語はすべて説明する。instruction が名指せる事実は、state が一行として印字しているものだけ。
- 選択肢：一つずつの項目。生成したものも含めすべてに、項目自身のテーブル行から書いた `what` / `not_for` を付ける。汎用的な例を少数付けるのは、選択肢がどの事実が当てはまるかで異なる場合だけ。一つの質問内で長さをほぼ揃えるのは出発点であって法則ではない。二つの質問を正しい方向に、二つを間違った方向に動かした（発見 26）ので、他と同様に測る。
- State：実際に組み上がったとおりのラン（各部屋、その戦闘、各扉とその先にあったもの）を渡し、Director 自身の答えの一覧は渡さない。Jev はそれを守るべき前例として読む（発見 31）。
- Instruction：公平な原則。ランについての原則は、state がランを印字していれば、その場所と、ないときは重みがないことを書いた上で入れてよい。まず履歴のないリクエストで測る（発見 32）。
- コード：安全のための制約、Jev が応えない系列の性質（連続、頻度の下限）、算術。どの state でも Jev が選ばない稀な選択肢には、言葉を足すのではなく頻度の下限を設ける（発見 27）。
- 答え：信頼度が 0.5 以上なら Jev の `choice`、それ未満なら分布そのまま。不確かさを温度で読み直さない（発見 33）。
- ラベル：対象を決め、ラベルはそこから読む。説明する対象と切り離して決めた約束は、Jev の安定した好みとともに繰り返す（発見 34）。
